Short answer: Reinstall / overwrite the app binary only. Leave %APPDATA%\sales-electron\ alone. On next launch, new schema migrations run automatically against the existing sales.db.

Why data survives an update
What	Where	Touched by installer?
App code (Electron + UI)
Program Files\… (or chosen install dir)
Yes — replaced
Production database
%APPDATA%\sales-electron\sales.db
No
The package name is sales-electron, so userData stays at:

%APPDATA%\sales-electron\sales.db
That folder is outside the install directory. NSIS updates replace the program files; they do not wipe AppData when you keep the same appId / product name.

On startup, initDatabase() opens that DB and runMigrations applies only migration files not yet recorded in schema_migrations. Existing rows are not wiped.

Practical update process today
This project does not ship auto-update (electron-updater is not wired). Current flow:

Bump version and build the installer (recommended):
  npm run release:minor
  (or release:patch / release:major / release -- minor)
  → bumps package.json + package-lock.json, then runs dist:win
  → release/Sales Management Application-Setup-{version}-win-x64.exe
Manual alternative: edit "version" in package.json, then npm run dist:win
On the user PC:
Prefer: quit the app, then run the new Setup (same options / overwrite).
Or: uninstall without deleting user data (if the uninstaller asks), then install the new build.
Launch once — migrations for anything new (e.g. `086_supervisor_overview.sql`, VCN layout) apply; sales/stock stay.
Do not run db:reset, delete sales.db, or copy a fresh DB over production.

Optional but wise before major releases: create an in-app backup (**General Parameters → Data backup**) or copy `%APPDATA%\sales-electron\` with the app closed so you can roll back if a migration fails.

Rules so updates stay safe
Same appId (com.sales-electron.app) and package name (sales-electron) — changing these can create a new empty userData folder and look like “lost data”.
Ship schema changes as numbered migrations under src/electron/db/migrations/, never by replacing sales.db.
Prefer additive migrations (new tables/columns); destructive ones need a tested upgrade path.
Keep productName / installer naming stable unless you intentionally migrate paths.
Later improvement (not built yet)
For less manual work you could add electron-updater (or a shared network folder of installers) so the app downloads and installs a new NSIS build. Data would still stay in AppData the same way — auto-update only replaces the app package.

**Automatic backups:** In-app daily schedule (**General Parameters → Data backup**, while the app runs) or IT script `scripts/backup-windows.ps1` via Task Scheduler when the app is closed. See [11-data-backup-restore.md](user-guide/11-data-backup-restore.md).

Bottom line: Ship a new Setup with a bumped version, install over the existing app, never touch %APPDATA%\sales-electron\. Migrations handle schema; business data stays put.
